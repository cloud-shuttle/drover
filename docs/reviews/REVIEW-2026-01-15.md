- **No epic bootstrap script referenced**  
  Both loaders expect a separate “epic creation” script but none exists in the branch. Even if recursion were fixed, epic IDs are never created/populated (`EPIC_IDS` map remains undefined), so all `drover add` commands would fail.

- **Duplicated loaders with divergent logic**  
  `load-tasks.sh` and `load-tasks-part2.sh` are near-duplicates but differ in how they build commands (`eval` vs. direct). Maintaining both increases drift risk; neither currently works.

- **Unimplemented features vs. design docs**

None of these code paths exist in the branch. This is a documentation-only delta, so the branch is not functionally aligned with the designs.

## DBOS & Beads Design Fidelity
- **DBOS alignment:** Core design (`design/DESIGN.md`) still positions DBOS as the durable workflow engine with per-task workflows and queue-based concurrency. The new design docs do not specify DBOS integration points for the proposed features (e.g., event bus durability, workflow cancellation semantics), leaving a gap between architectural goals and planned work. No new DBOS-related code landed in this branch to validate against the design.
- **Beads alignment:** Existing Beads sync supports bidirectional JSONL import/export with hierarchical task IDs and dependency links (e.g., `beadsStatusToDrover`, `droverStatusToBeads`). The new docs introduce additional task semantics (context carrying, verdicts, research task type) without mapping them to Beads structures or sync rules. Risk: divergence between Drover’s task model and Beads state unless the schema and sync logic are updated alongside new features.
